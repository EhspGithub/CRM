# سامانه مدیریت کلینیک ترک اعتیاد «نسیم رهایی» — اپ ویندوز و اندروید

نسخهٔ نصبی سامانهٔ نسیم رهایی: پرونده مراجعین، پذیرش، ویزیت، ارائه دارو، مدیریت اپیوم، گزارش‌گیری، کنترل کیفیت پرونده‌ها و پشتیبان‌گیری — با **دیتابیس SQLite واقعی** روی همان دستگاه، بدون نیاز به اینترنت.

| | |
|---|---|
| ویندوز | نصب‌کنندهٔ `.exe` (و `.msi`) |
| اندروید | فایل `.apk` (اندروید ۷ به بالا) |
| دیتابیس | SQLite (فایل `nasim.db`) + نقاط بازگشت خودکار |
| شبکه | هیچ؛ اپ به اینترنت وصل نمی‌شود |

## دریافت و نصب

1. در گیت‌هاب به تب **Actions** بروید، آخرین اجرای موفق **Build** را باز کنید و از بخش **Artifacts** فایل‌ها را دانلود کنید:
   - `windows-installer` ← داخلش `Nasim Rahayi_x.y.z_x64-setup.exe`
   - `android-apk` ← داخلش `NasimRahayi-x.y.z.apk`
   (برای نسخه‌های منتشرشده با تگ `v…`، همین فایل‌ها در بخش **Releases** هم هستند.)
2. **ویندوز:** فایل setup را اجرا کنید. اگر پیام «Windows protected your PC» آمد: «More info ← Run anyway».
3. **اندروید:** فایل apk را روی گوشی باز کنید و اجازهٔ «نصب از منابع ناشناس» را بدهید.

## انتقال اطلاعات از نسخهٔ HTML

اپ نصبی در اولین اجرا با دیتابیس **خالی** شروع می‌شود (داده‌های نمونه ندارد). برای آوردن اطلاعات کلینیک:

1. در نسخهٔ قبلی (فایل `CRM-online…html` در مرورگر) دکمهٔ **پشتیبان‌گیری** (آیکون دانلود بالای صفحه) را بزنید تا فایل `nasim_rahayi_backup_….json` ذخیره شود.
2. در اپ: **تنظیمات ← ورود و خروج اطلاعات ← بازیابی / ادغام دیتابیس** و همان فایل را انتخاب کنید.
3. «بازیابی کامل» را بزنید. همهٔ مراجعین، ویزیت‌ها، تماس‌ها، تاریخچه‌ها، اپیوم، تنظیمات و کادر درمان منتقل می‌شوند.

همین فایل پشتیبان بین ویندوز و اندروید هم جابه‌جا می‌شود. برای کار هم‌زمان روی دو دستگاه، از «ادغام هوشمند» استفاده کنید.

## محل ذخیرهٔ اطلاعات و پشتیبان‌گیری

- **دیتابیس:** ویندوز `%APPDATA%\com.nasimrahayi.clinic\nasim.db` — اندروید: حافظهٔ خصوصی اپ.
- هر تغییر **همان لحظه** در دیتابیس ذخیره می‌شود (حالت WAL، مقاوم در برابر قطعی برق و بسته شدن ناگهانی).
- **نقاط بازگشت خودکار:** چند ثانیه بعد از هر تغییر، روزانه، و پیش از هر بازیابی/ادغام/پاکسازی، یک نسخهٔ کامل JSON در پوشهٔ `backups` کنار دیتابیس ساخته می‌شود (۴۰ نسخهٔ آخر). از «تنظیمات ← ورود و خروج اطلاعات» دیده و بازیابی می‌شوند.
- نقاط بازگشت روی **همان دستگاه** هستند. برای محافظت در برابر خرابی یا گم شدن دستگاه، هر هفته با دکمهٔ **پشتیبان‌گیری** یک فایل روی فلش، فضای ابری یا دستگاه دیگری ذخیره کنید.
- ⚠️ در اندروید، حذف اپ (Uninstall) دیتابیس را هم پاک می‌کند. قبل از حذف حتماً پشتیبان بگیرید.

## معماری

```
src-tauri/                 برنامهٔ بومی (Rust + Tauri 2)
  src/lib.rs               فرمان‌ها: db_execute / db_select / db_batch / backup_snapshot / backup_list / backup_read
  crates/nasim-db/         دسترسی SQLite (rusqlite، SQLite داخلی) + نقاط بازگشت؛ با تست
src/                       لایهٔ وب (Vite)
  main.js                  راه‌اندازی: فونت‌ها و کتابخانه‌ها (همه محلی)، باز کردن دیتابیس، بارگذاری UI
  db/schema.js             اسکیمای SQLite و migrationها
  db/store.js              getAll / put / putAll / delete / replaceAll روی SQLite (صف ترتیبی، تراکنش)
  db/drivers/              tauri (فایل SQLite واقعی) و sql.js (مرورگر و تست‌ها)
  platform/                دیالوگ ذخیره/باز کردن بومی، چاپ اندروید
  styles/app.css           Tailwind + استایل‌های سامانه + لایهٔ موبایل
public/app/00…16-*.js      منطق سامانه، تفکیک‌شده بر اساس بخش (داشبورد، مراجعین، اپیوم، گزارش‌ها، …)
index.html                 ساختار صفحه
tests/                     تست واحد (vitest)، تست کامل UI و تست مسیرهای اپ نصبی (Chrome)
```

- هر «مخزن» نسخهٔ قبلی (مراجعین، ویزیت‌ها، …) یک **جدول SQLite** است: رکورد کامل در ستون `data` (JSON معتبر با `CHECK`) و فیلدهای جستجو و ارتباط در ستون‌های ایندکس‌دار (`patient_id`، `code`، `national_id`، `date`، …).
- بازیابی و ادغام بکاپ در **یک تراکنش** انجام می‌شود: یا کامل اعمال می‌شود یا هیچ تغییری نمی‌کند.
- نوشتن‌ها به‌ترتیب صادر شدن اعمال می‌شوند و هر خواندن، همهٔ نوشتن‌های قبلی را می‌بیند.

## توسعه

پیش‌نیاز: Node 20+، Rust (stable)، و برای اندروید Android SDK/NDK.

```bash
npm install
npm run dev          # UI در مرورگر (SQLite روی WebAssembly، با داده‌های نمونه)
npm run app:dev      # اپ ویندوز در حالت توسعه
npm test             # تست‌های لایهٔ داده
npm run build && CHROME_PATH=/path/to/chrome npm run test:e2e      # تست کامل UI (دسکتاپ + گوشی)
npm run build && CHROME_PATH=/path/to/chrome npm run test:native   # مسیرهای اپ نصبی
cd src-tauri && cargo test -p nasim-db                             # تست‌های Rust
npm run app:build    # نصب‌کنندهٔ ویندوز
```

## ساخت خودکار و انتشار نسخه

گردش‌کار `.github/workflows/build.yml` روی هر push:

1. تست‌ها: لایهٔ داده، Rust (+clippy)، بیلد UI، تست کامل UI در Chrome (دسکتاپ و گوشی)، تست مسیرهای اپ نصبی، `npm audit`
2. ساخت نصب‌کنندهٔ ویندوز (`.exe` و `.msi`) روی `windows-latest`
3. ساخت APK اندروید (arm64 + armv7) و امضای آن

برای انتشار نسخه: `version` را در `package.json` بالا ببرید، در `CHANGELOG.md` ثبت کنید، سپس:

```bash
git tag v1.0.1 && git push origin v1.0.1
```

فایل‌ها به‌صورت خودکار در **Releases** منتشر می‌شوند.

## کلید امضای اندروید

اندروید فقط نسخه‌ای را به‌عنوان «به‌روزرسانی» نصب می‌کند که با **همان کلید** نسخهٔ قبلی امضا شده باشد. بدون کلید ثابت، هر ساخت با یک کلید موقت امضا می‌شود (برای تست مناسب است) و برای نصب نسخهٔ بعدی باید اپ را حذف کنید — که **داده‌ها را پاک می‌کند**. پس قبل از استفادهٔ جدی، این سه Secret را در «Settings ← Secrets and variables ← Actions» ریپو بسازید:

| Secret | مقدار |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | محتوای فایل keystore به‌صورت base64 |
| `ANDROID_KEYSTORE_PASSWORD` | رمز keystore |
| `ANDROID_KEY_ALIAS` | نام کلید (alias) |

ساخت keystore (یک‌بار، روی سیستمی که JDK دارد):

```bash
keytool -genkeypair -keystore nasim-release.jks -alias nasim -keyalg RSA -keysize 4096 -validity 10000
base64 -w0 nasim-release.jks   # خروجی را در ANDROID_KEYSTORE_BASE64 بگذارید
```

فایل keystore و رمزش را جای امنی نگه دارید: **با گم شدن آن دیگر نمی‌توانید به‌روزرسانی منتشر کنید.** هرگز آن را در ریپو commit نکنید (`.gitignore` جلوی `*.jks` را گرفته است). اگر برای اپ رزیدنتی keystore ساخته‌اید، می‌توانید همان را این‌جا هم استفاده کنید.

## امنیت و حریم خصوصی

- اطلاعات بیماران فقط روی همین دستگاه است؛ اپ هیچ سرور، حساب کاربری یا دسترسی شبکه‌ای ندارد (مجوز HTTP اصلاً فعال نیست).
- دسترسی فایل فقط به فایلی است که کاربر خودش در پنجرهٔ ذخیره/باز کردن انتخاب می‌کند؛ نام نقاط بازگشت را خود اپ می‌سازد و مسیر دیگری خوانده نمی‌شود.
- تمام SQLها پارامتری‌اند؛ نام جدول و ستون فقط از اسکیمای ثابت می‌آید.
- فایل‌های پشتیبان شامل اطلاعات کامل بیماران‌اند؛ آن‌ها را عمومی به اشتراک نگذارید.
- چون رابط کاربری سامانه از رویدادهای inline (`onclick`) استفاده می‌کند، CSP اجازهٔ اسکریپت inline را دارد، اما هیچ اسکریپتی از بیرون اپ بارگذاری نمی‌شود و همهٔ داده‌های ورودی پیش از نمایش escape می‌شوند.
